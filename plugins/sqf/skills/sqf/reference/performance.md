# Производительность

Сначала измеряй: `diag_codePerformance [{ код }, args, 10000]` (в debug console есть
кнопка), `diag_fps`, `diag_activeScripts`, `diag_activeSQFScripts`.

## Правила

- **Кешируй дорогие запросы.** `allUnits`, `allPlayers`, `vehicles`, `allMissionObjects`,
  `nearestObjects`, `nearEntities`, `entities`, `lineIntersectsSurfaces` — не вызывай их
  каждый кадр и во вложенных циклах. `nearEntities` намного дешевле `nearestObjects`.
- **Расстояния**: `distanceSqr` без извлечения корня; `distance2D`, если высота не важна.
  Сначала дешёвые проверки, потом дорогие (и ленивые `&& {}`).
- **Ранний выход**: `findIf` вместо `{...} count _arr > 0` или полного `forEach` с флагом.
- **Поиск**: `get` / `in` по hashmap вместо `find` по длинному массиву.
- **Сборка массивов**: `pushBack`/`append`; `apply`/`select` для map/filter.
  Не делай `_arr = _arr + [_x]` в циклах (каждый раз копирование).
- **Строки**: в циклах собирай через массив + `joinString`; без `+` в циклах и без `format`
  в горячих циклах. Для пары кусков `+` нормально. Длинные строки — не через `format`
  (лимит длины, см. syntax-pitfalls.md).
- **Функции**: CfgFunctions / `compileFinal` один раз; никогда не `execVM` и не
  `compile preprocessFileLineNumbers` повторно в цикле.
- **Меньше скриптов**: один управляющий цикл по N объектам лучше N spawn-циклов.
- **Горячие unscheduled-пути** (EachFrame, Draw3D, HandleDamage, Fired): минимум кода;
  никаких `nearestObjects`, `format`/`diag_log` каждый кадр.
- **Сеть**: объединяй `publicVariable` / `setVariable [.., true]` / `remoteExec`;
  отправляй только при изменении; никогда из покадрового цикла.
- **Объекты**: `createSimpleObject` / `enableSimulationGlobal false` / dynamic simulation
  для статичных объектов; `hideObjectGlobal` вместо удаления и пересоздания. Удаляй то, что создал.
- **Маркеры**: `createMarkerLocal` + `setMarker*Local` для настройки, затем одна глобальная
  команда в конце для синхронизации (каждая глобальная команда маркера — сетевое сообщение).
- **params вместо select**: `params` быстрый и проверяет типы; повторный `_this select N`
  медленнее и небезопасен.
- **Не оптимизируй вслепую**: сначала читаемость, замеряй только горячие участки.

## Уровень миссии (по BIKI: Mission Optimisation)

### Где искать проблему

- Проверь миссию в одиночной игре: если в SP всё хорошо, а в MP плохо — виноваты сетевые
  сообщения или сервер, а не графика.
- Проверь без модов: плохо оптимизированные моды часто съедают больше, чем миссия.
- Высокая дальность видимости нагружает **и CPU, и GPU**. Её можно задавать каждому клиенту
  отдельно (`setViewDistance`, `setObjectViewDistance` на клиенте) независимо от сервера.
  Дальность объектов разумно держать в 1/3–1/2 от дальности ландшафта.
- Инструменты: `#monitor 5` (в игре, у админа) и `#monitords 5` (в консоли выделенного
  сервера) — производительность сервера, `0` — выключить; `diag_activeScripts`,
  `diag_activeSQFScripts`, `diag_activeSQSScripts`, `diag_activeMissionFSMs` — сколько
  скриптов запущено; профайлер — ArmaScriptProfiler (Dedmen).

### ИИ и объекты

- Меньше объектов — больше FPS. Считаются и юниты/агенты, и техника, и обвесы на оружии
  (их прокси — `attachTo`), и снаряжение, и ПНВ.
- Где ИИ не нужна логика группы — агенты (`createAgent`) вместо юнитов.
- Каждый юнит — сетевые обновления: нагрузка и на CPU, и на сеть.
- Игрок со слабым ПК не должен командовать большой группой ИИ — она считается у него локально.
- Dynamic Simulation замораживает удалённых от игроков ИИ и объекты; дистанции подбирай под миссию.
- ИИ можно вынести на headless client (`setGroupOwner`, см. multiplayer.md).
- Статичные декорации — simple objects. Трупы и обломки — garbage collector
  (встроенный в Eden или свой серверный).
- GPU сильно нагружают только объекты на экране.

### Скрипты

- Не запускай по скрипту на юнит — один скрипт с массивом, который пополняется/чистится:
  ```sqf
  { _x spawn TAG_fnc_myCode; } forEach _units;   // плохо
  _units spawn TAG_fnc_myCode;                    // хорошо
  ```
- Не `execVM` в цикле (файл читается каждый раз): `compile` один раз → лучше, функция из CfgFunctions → идеально.
- Цикл без паузы — почти всегда ошибка проектирования:
  ```sqf
  while {true} do {...};               // плохо, если не уверен
  while {alive player} do {...};       // лучше
  while {sleep 1; alive player} do {...};   // хорошо
  ```
  Нужна ли покадровая точность, или задержка в секунду-две допустима?
- Триггеры проверяют условие каждые 0.5 с. Большая зона или сложное условие → переделай
  на скрипт или увеличь интервал (`setTriggerInterval`, атрибут в 3DEN, с v2.00).
  Триггеры, нужные только серверу, делай server-only.
- Вся логика миссии (задачи, захват, расчёты завершения) — на сервере. На клиенте — только
  локальные эффекты.
- Unscheduled-код не ограничен планировщиком: тяжёлый циклический unscheduled-код может
  заморозить игру. В EH быстро получи нужные данные, остальное — `spawn`.

### Сеть

- `publicVariable` — только когда нужно; адресно — `publicVariableServer` / `publicVariableClient`.
- Глобальное создание юнитов/техники синхронизируется по сети — держи его минимальным,
  лучше в один момент (например, на старте).
- Команды с глобальным эффектом — точечно. Частый `setPos` синхронизирует позицию всем
  клиентам; если объект должен следовать за другим — `attachTo`.
- Глобальные команды маркеров отправляют маркер целиком: настраивай локальными командами,
  последней — одна глобальная.
- `BIS_fnc_MP` устарел — только `remoteExec` / `remoteExecCall`.
