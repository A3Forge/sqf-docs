# Мультиплеер: локальность, сеть, безопасность

## Машины

| Проверка | Значение |
|---|---|
| `isServer` | сервер (выделенный или хост в игре, поднятой игроком) |
| `isDedicated` | выделенный сервер (нет игрока, нет UI) |
| `hasInterface` | есть игрок/UI (клиент или хост); false на выделенном сервере и headless-клиентах |
| `!hasInterface && !isServer` | headless-клиент |
| `isMultiplayer` | сетевая сессия |
| `clientOwner` | owner ID этой машины (у сервера 2) |
| `owner _obj` | owner ID объекта (только на сервере) |
| `local _obj` | объект локален для этой машины |

Хост (игра, поднятая игроком) — одновременно сервер **и** клиент: код должен работать,
когда оба флага истинны.

## Локальность команд

У каждой команды на вики есть значки:

- **AL** — аргумент должен быть локальным (иначе команда молча ничего не делает)
- **AG** — аргумент может быть любым объектом
- **EL** — эффект только на этой машине
- **EG** — эффект рассылается на все машины
- **SE** — выполняется только на сервере

Примеры: `setFuel` AL/EG, `setDamage` AG/EG, `addAction` AG/EL, `hint` EL,
`setVehicleLock` AL/EG, `addWeapon` AL/EG, `setObjectTexture` AG/EL (для EG —
`setObjectTextureGlobal`), `createVehicle` EG, `createVehicleLocal` EL,
`setVariable` EL, если не указан флаг public.

Перед использованием команды на объектах, которые могут быть удалёнными, всегда сверяйся
с локальностью на вики.

### Кому что принадлежит

- Юнит локален на машине, которая управляет лидером его группы (группы ИИ — сервер или HC).
- Юнит игрока локален у этого игрока.
- Техника локальна у водителя (или фактического командира); пустая техника — обычно у сервера или последнего водителя.
- Локальность меняется во время игры (смена водителя, группы, отключение игрока).
  Проверяй `local` заново, не кешируй. При смене срабатывает EH `Local`.

## remoteExec

```sqf
[_args] remoteExec ["TAG_fnc_name", _target, _jip];
[_args] remoteExecCall ["TAG_fnc_name", _target, _jip];   // unscheduled на цели
[_veh, 0.5] remoteExec ["setFuel", _veh];                  // выполнить там, где _veh локален
```

Цели:

| `_target` | Где выполняется |
|---|---|
| `0` | везде (включая сервер) |
| `2` | только сервер |
| `-2` | везде, кроме сервера |
| id из `clientOwner` | на этом клиенте |
| объект | на машине, где объект локален |
| группа / side / массив | у членов / у всех из них |

Параметр JIP: `true` (авто-ID), строка-ID (заменяет предыдущий вызов с тем же ID в очереди),
или объект/группа/netId (удаляется из очереди при удалении объекта).
Удалить JIP-запись: `remoteExec ["", "jipID"]`.

Правила:
- Предпочитай `remoteExec` **функции из CfgFunctions**, а не команды с кодом в аргументах.
- Никогда не отправляй код на выполнение: `remoteExec ["call", ...]` / `["spawn", ...]`
  с кодом — дыра в безопасности, и любой нормальный `CfgRemoteExec` это блокирует.
- `remoteExec` с сервера на цель `2` (сам себе) просто выполняется локально — это нормально.
- Не вызывай `remoteExec` с JIP в цикле или каждый кадр — очередь JIP растёт бесконечно.
- `remoteExecutedOwner` внутри вызванной функции = owner ID отправителя
  (0, если функция вызвана не через remoteExec).

### Проверка на сервере

```sqf
// fn_requestBuy.sqf — выполняется на сервере через remoteExec от клиента
params [["_unit", objNull, [objNull]], ["_item", "", [""]]];
if (!isServer) exitWith {};
if (isNull _unit || {owner _unit != remoteExecutedOwner}) exitWith {};   // вызывающий владеет _unit
if !(_item in TAG_allowedItems) exitWith {};
...
```

### CfgRemoteExec (description.ext / config.cpp)

```cpp
class CfgRemoteExec {
    class Functions {
        mode = 1;          // 0 = запретить всё, 1 = белый список, 2 = разрешить всё
        jip = 0;
        class TAG_fnc_requestBuy { allowedTargets = 2; };   // 0 любые, 1 только клиенты, 2 только сервер
    };
    class Commands {
        mode = 1;
        class setFuel { allowedTargets = 0; };
    };
};
```

## Данные на стороне клиента: uiNamespace и profileNamespace

Обе области **на клиенте** игрок контролирует **до** захода на сервер (на выделенном
сервере `uiNamespace` сервера игроку недоступен — там его можно использовать, например,
чтобы сохранить данные между миссиями):

- `uiNamespace` живёт, пока запущена игра, и переживает смену миссий. Его можно заполнить
  в редакторе, в другой миссии, на другом сервере или локальным модом, а потом
  зайти на ваш сервер с уже подменёнными значениями.
- `profileNamespace` хранится в файле профиля (`*.vars.Arma3Profile`) на диске игрока —
  его можно отредактировать вручную.

Поэтому:

- **Никогда не храни там то, что выполняется**: код для `call`/`spawn`, строки для
  `compile`/`execVM`, имена функций, которые потом вызываются через
  `missionNamespace getVariable`, обработчики событий. Подменённое значение выполнится
  с правами вашей миссии.
  ```sqf
  // ПЛОХО: игрок подложит свой код в uiNamespace до захода
  private _fnc = uiNamespace getVariable ["TAG_fnc_cached", {}];
  call _fnc;

  // ПЛОХО: имя функции из профиля
  call (missionNamespace getVariable (profileNamespace getVariable ["TAG_lastAction", ""]));
  ```
  Функции — только через CfgFunctions / `compileFinal` / рассылку с сервера.
- **Не бери оттуда ничего важного**: права, админ-флаги, деньги, опыт, роли, разблокировки,
  кулдауны, баны. Всё это — только на сервере (база данных, серверные переменные).
- **Допустимо**: простые флаги и настройки удобства, подмена которых ничего не даёт игроку.
  При чтении проверяй тип и подставляй значение по умолчанию:
  ```sqf
  // Игрок один раз согласился с правилами — больше не показываем окно
  private _accepted = profileNamespace getVariable ["TAG_rulesAccepted_v3", false];
  if !(_accepted isEqualType true) then {_accepted = false};
  if (!_accepted) then {
      [] call TAG_cl_showRules;   // по кнопке «Согласен»:
      // profileNamespace setVariable ["TAG_rulesAccepted_v3", true]; saveProfileNamespace;
  };
  ```
  Подмена такого флага максимум скроет окно с правилами — это не уязвимость. Если же факт
  согласия важен юридически или для доступа к игре — храни его на сервере (в БД по UID).
  Версия в имени ключа (`_v3`) позволяет заново показать правила после их изменения.
- Значения из этих пространств, отправленные на сервер, — такой же недоверенный ввод,
  как любые аргументы `remoteExec`.
- `saveProfileNamespace` пишет файл на диск — вызывай редко (по действию игрока), не в цикле.

## Публичные переменные

```sqf
TAG_state = 1; publicVariable "TAG_state";          // всем + JIP
publicVariableServer "TAG_req";                      // клиент → сервер
_ownerId publicVariableClient "TAG_reply";           // сервер → один клиент
"TAG_state" addPublicVariableEventHandler { params ["_name", "_value"]; };  // у отправителя не срабатывает
_obj setVariable ["TAG_hp", 100, true];              // рассылка + JIP
_obj setVariable ["TAG_hp", 100, [2, _owner]];       // на конкретные машины
```

- Каждая публичная переменная / setVariable с рассылкой — сетевой трафик и запись для JIP.
  Объединяй изменения; не рассылай в быстрых циклах.
- Массивы и hashmap передаются по значению; локальное изменение после рассылки не синхронизируется.

## Порядок инициализации (миссия)

1. Функции `preInit` (unscheduled), на всех машинах
2. Init-поля объектов (на каждой машине, включая JIP-клиентов — **команды с глобальным
   эффектом там выполнятся N раз**; оборачивай в `if (isServer)` или `if (local this)`)
3. `init.sqf` (все машины, scheduled) — лучше использовать специализированные файлы ниже
4. `initServer.sqf` (сервер)
5. `initPlayerLocal.sqf` — `params ["_player", "_didJIP"];` (клиент, `player` здесь уже валиден)
6. `initPlayerServer.sqf` — сервер, для каждого подключившегося игрока (выполняется через
   remoteExec; избегай тяжёлой логики, он медленный и с задержкой)
7. Функции `postInit`

Респаун: скрипты событий `onPlayerRespawn.sqf` / `onPlayerKilled.sqf` или EH `Respawn`
(не все EH, добавленные на юнита, переносятся на нового — при респауне добавляй заново).

## Event handlers и локальность

- `Killed`, `Hit`, `HandleDamage`, `GetIn` и т.д. срабатывают там, где юнит/техника **локальны**.
  Если нужно на всех машинах — `MPKilled` / `MPHit` (`addMPEventHandler`).
- `HandleDamage` срабатывает несколько раз за одно попадание (по каждой hit selection),
  и его возвращаемое значение заменяет урон — последнее выражение должно быть числом урона.
- `addAction` локален: добавляй его на каждом клиенте (и для JIP) — например через
  `remoteExec` с JIP на объект или в `initPlayerLocal.sqf`. Код действия выполняется только
  у клиента, который его использовал; для влияния на сервер — `remoteExec`.
- Mission EH (`EntityKilled`, `PlayerConnected`, `HandleDisconnect`) — проверяй, где каждый срабатывает.

## Headless-клиенты

Группы ИИ передаются через `_grp setGroupOwner _hcOwnerId` (только на сервере).
После передачи AL-команды на этих юнитах должны выполняться на HC.

## Смена миссии, рестарт и загрузка миссии клиентами

- **`skipLobby = 1;`** в `description.ext` — игрок не выбирает слот: сразу получает
  первый свободный и попадает в миссию.
- Смена миссии с сервера — `_password serverCommand format ["#mission %1", _name]`
  (`_name` — `имя.мир`). Клиенты остаются на сервере и грузят следующую миссию, в
  главное меню не выходят.
- Плановый рестарт процесса: `#shutdownaftermission`, затем кик всех
  (`#kick <uid> <причина>`) и `endMission`. Процесс завершается, его поднимает внешний
  рестартер. Клиент видит «Вас изгнали из игры. (<причина>)» — по причине клиентский мод
  может отличить рестарт от обычного кика (см. ui-mods.md).
- **Двойная смена миссии** (например, `#restart` или старт процесса, после которого
  скрипт сразу делает `#mission` на сохранённую миссию) подвешивает клиентов на экране
  загрузки на минуты. Одиночный `#mission` проходит чисто. Если миссия восстанавливается
  после рестарта, восстанавливай её до того, как подключатся игроки.
- **HTTP-зеркало миссий** (`missionHTTPDownloadBaseURL` в `server.cfg`): сервер ждёт,
  пока **все** клиенты получат файл миссии. Если у одного клиента загрузка с зеркала
  висит (таймаут сети, не проходит TLS, провайдер, антивирус), старт миссии ждёт его
  таймаута — вплоть до ~5 минут у всех. В RPT сервера видны только неудачи загрузки
  (`Operation timed out…`, `Connection timed out…`, ошибки schannel); успешные загрузки не
  логируются. Миссия стартует в ту же секунду, когда у последнего клиента загрузка
  обрывается.
- RPT сервера не пишет подключения и отключения игроков: если они нужны для разбора,
  логируй их сам (`PlayerConnected` / `HandleDisconnect`).
